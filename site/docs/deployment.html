Deployment

Karbon builds to a single Rust binary that fronts the whole app. karbon deploy targets a VPS over SSH, a Docker image, or a PaaS — generating the configs you need.

Build for production

karbon build   # frontend build + cargo build --release
karbon serve   # run on a single port (reverse proxy to Node SSR built in)

For a micro skeleton there's no frontend step — it's just the release binary.

Deploy to a VPS

karbon deploy publish         # rsync artifacts (no rebuild)
karbon deploy publish:build   # build then publish
karbon deploy ssh             # legacy alias of publish:build

Configure the target in karbon.toml:

[deploy]
path = "/var/www/my-app"
user = "www-data"                    # optional — owner for chown
group = "www-data"                   # optional — defaults to user
manager = "pm2"                      # "pm2" or "systemd"
pm2_config = "ecosystem.config.cjs"  # PM2 file (default)
service = "my-app"                    # systemd service name (default: app.name)
host = "user@server"                 # optional — omit for a local deploy

If user is set, chown -R user:group runs after the sync (group falls back to user). The process manager is either PM2 (with the given ecosystem file) or systemd (the named service).

Hardened scripts. Every value injected into a shell command passes through validate_shell_safe(), and the database password is passed via an environment variable (MYSQL_PWD) rather than a command-line argument.

Docker

karbon deploy docker   # multi-stage Dockerfile + .dockerignore

Generates an optimised multi-stage build: a builder stage compiles the release binary (and the frontend, unless micro), and a slim runtime stage runs it. The backend-only case produces a backend-only image.

PaaS

karbon deploy paas      # generate fly.toml, render.yaml, Procfile
karbon deploy fly       # deploy via flyctl (generates config as needed)
karbon deploy railway    # deploy via railway up

Production checklist

  • Set APP_ENV=production — internal error details are then hidden from clients.
  • Set a strong JWT_SECRET (or leave empty to disable auth deliberately).
  • Provide database credentials via DATABASE_URL or DB_*.
  • Run karbon migrate on the target before serving traffic.
  • Run karbon doctor --db to confirm connectivity and that no migrations are pending.
  • Decide on rate limiting based on your proxy/NAT topology (it's opt-in).
  • Terminate TLS at your proxy or platform — cookies become Secure over HTTPS automatically.

Because the Rust binary reverse-proxies the frontend, you operate one service in production. See Frontend & rendering for how the single-port model works.
