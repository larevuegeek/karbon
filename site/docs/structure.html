Project structure

A karbon new project keeps the Rust backend, the frontend and the tooling config in predictable places. Here's what each part is for.

A full-stack project

my-app/
├── karbon.toml            # project config (frontend, backend, deploy)
├── .env / .env.example    # environment variables (cascade loaded)
├── app/                   # the Rust backend crate
│   ├── Cargo.toml
│   └── src/
│       ├── main.rs        # entry point — App::new()…serve(); route markers live here
│       ├── entity/        # entities (the source of truth for migrations)
│       ├── repository/    # CrudRepository impls
│       ├── controller/    # #[karbon::controller] handlers
│       └── welcome.html   # welcome page (micro skeleton)
├── frontend/              # SvelteKit (or Next.js) app
│   ├── package.json
│   ├── vite.config.ts
│   └── src/
├── migration/             # versioned .sql migrations
└── docs/                  # Markdown docs → karbon docs build → docs/_site/

A --skeleton micro project has no frontend/ and no [frontend] section in karbon.toml; the backend serves an HTML welcome page directly. dev, build, serve and deploy all handle the no-frontend case.

karbon.toml

The single config file that the CLI reads. A typical full project:

[app]
name = "my-app"

[backend]
# extra binaries to build & deploy alongside the main one
extra_packages = []

[frontend]
framework = "svelte"      # or "nextjs"; absent for micro skeletons

[deploy]
path = "/var/www/my-app"
manager = "pm2"           # "pm2" or "systemd"
host = "user@server"      # omit for a local deploy

See Configuration for the full reference and Deployment for the [deploy] options.

The backend crate (app/)

app/src/main.rs is the kernel: it builds the App, mounts modules and routes, and serves. The generators keep it in sync using marker comments — you rarely edit route wiring by hand:

// karbon:routes        → web/admin controllers are nested here
// karbon:api-routes    → API controllers are nested here
// karbon:openapi-api    → OpenAPI path aggregation (API)
// karbon:openapi-root   → OpenAPI path aggregation (root)

When you run generate controller, crud or admin, the new routes and OpenAPI paths are inserted at these markers automatically. Routes are mounted with .nest(prefix, router), never .merge().

entity/

Plain Rust structs with an id field and a #[table_name("…")]. They are the source of truth for the schema: karbon migrate diff parses them and compares against the live database. See Database & ORM.

controller/

Each controller is an impl block annotated with #[karbon::controller(prefix = "…")]. The macro generates the router, prefix and OpenAPI paths. See Routing & controllers.

The framework crate

Your project depends on the framework under the alias karbon so the macros (which emit karbon:: paths) resolve:

[dependencies]
karbon = { package = "karbon-framework", version = "0.2", features = ["…"] }

Feature flags pick the database driver (postgres, sqlite — MySQL is default), the template engine, and optional components (studio, redis, scraping, …). The scaffolding writes the right alias and imports for you.

docs/

Markdown files here are rendered two ways: karbon docs build turns them into a static site under docs/_site/, and the same sources feed the Docs tab inside Studio. New projects ship a starter docs/index.md.
